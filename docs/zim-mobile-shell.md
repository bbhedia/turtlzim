# The mobile shell (Android first, then iPhone)

The web app (`web/`) in an app of the phone's store: a Capacitor 8 project in `mobile/` whose web files are the build of `web/`,
unchanged. There is **one editor** (CodeMirror 6, `docs/zim-editor-plan.md`); the shell adds what a store app has and a WebView lacks.
Decided 2026-10-13, after asking whether Flutter would be better for native apps: it would not, for this project (below), and the user
chose to go on with the shell. Android is built and tried here; **iOS** is built and tried in a simulator by a macOS CI job (below: no Mac is needed for that, an account on an iPhone is tried there against a real server, and no iPhone has been tried).

## Why not Flutter (for now)

- The Rust core is shared either way (Flutter calls it through FFI, `flutter_rust_bridge`; the shell through JNI/Swift), and the iOS
  build of the core does not exist yet in both cases. What Flutter would change is the **editor**, the largest piece of the project
  (CLAUDE.md, risk 7): ours is CodeMirror 6, where the document *is* the text of the Zim file (never a tree that is written back), with live
  formatting, tables as a grid, pictures, a folded header, link completion and one undo for one action. Flutter's rich-text editors
  (flutter_quill, super_editor, appflowy_editor) have a document model of their own, which is the round trip that this project
  refuses, and a styled `TextField` does not take blocks (tables, pictures) well. That is a rewrite of weeks to months, a second
  suite of tests next to the 494 unit tests and the 113 browser scenarios (97 of them in WebKit as well), and, if web and desktop keep
  CodeMirror, two editors to keep identical byte for byte.
- What Flutter would give is the system's handling of the keyboard, focus and insets, which the web app does with `visualViewport`
  (`web/src/app/viewport.ts`). That is tried in a real Android WebView first (below), and the user found the web app fine on a phone.
- To revisit if a device test shows the editor in a WebView to be unacceptable: a time-boxed Flutter prototype of the editor alone
  would give the real cost before anything is decided.

## What the shell is

| | |
|---|---|
| Project | `mobile/` (Capacitor 8, `appId` `org.zimnotebook.app` — a placeholder to change before a store release —, Android and iOS) |
| Web files | `mobile/www/`, made by `mobile/scripts/prepare.mjs` from `web/dist` (so `npm run build` in `web/` comes first) |
| Shell script | `mobile/shell/shell.ts`, bundled to `www/shell.js` and loaded **before** the app: it sets `window.__zimShell` (below) |
| Shell mode of the app | `web/src/app/shell.ts`: the page knows that it is in a shell by `window.Capacitor` (which the WebView has before any script runs); the web app depends on no Capacitor package |
| Android project | `mobile/android/` (generated by `cap add android`, then edited: manifest, theme, icons) |
| iOS project | `mobile/ios/` (generated by `cap add ios`: iOS 17, the app's icon and launch picture, a shared scheme; the iPhone app, below) |

**What is different in the shell**

- **No service worker.** The code of the app is in the app, and only an update of the app changes it; a worker would keep a second copy.
  The PWA module says `native` (`web/src/pwa/register.ts`), the menu has no "Install the app", and *About this version* says which build
  this is (the app's version and the fingerprint of the web build inside it) and that the code is the app's.
- **The page's content policy is in the page.** The web server sends a `Content-Security-Policy` header; a WebView has no server, so
  `prepare.mjs` puts the same policy (it is exported by `web/scripts/serve.mjs`, `frame-ancestors` apart, which a `<meta>` can't carry) in
  `index.html`.
- **One permission in the manifest, `INTERNET`**, for the app's own requests to an account server that the person typed the address of (below; since E17). The web files are
  in the app and the page asks the network for nothing (its content policy allows none), so without an account the app does not use it. Nothing else is asked for (the other line that
  `aapt2 dump permissions` shows is the app's own, which AndroidX adds). And **no automatic backup**
  (`allowBackup="false"`): the notebooks and the encrypted vault stay in this app's storage and are not sent to a cloud backup; to keep a copy,
  export a notebook (zip) or back the vault up (a file that is still encrypted).
- **Files are handed to the system's own sheet**, not downloaded: a WebView does nothing with a link to a Blob that has `download`, which is
  how a browser saves a file. `window.__zimShell.saveFile(name, blob)` (set by `shell.ts`) writes the file to the app's cache folder
  (`handed-over/<time>/<name>`) and opens the share sheet on it (Filesystem and Share plugins), where the person saves it to *Files* or *Drive*
  or sends it. Export (zip), the page's *Download*, an attachment's *Download* and the vault backup all go through it. The folder is emptied
  each time the app starts, and the file lives in the app's private cache until then (a plain copy of an encrypted notebook, after the person
  said they wanted one). A file is read to base64 in memory first, so a very large one is a limit.
- **The back gesture** closes a dialog that is open, else goes back in the history of the pages (the app keeps an address per page), as in a browser, and
  leaves the app at the first (`shell.ts`: left alone, Capacitor leaves at once, whatever the history holds).
- **Icons and the start screen** are the web app's icon (`mobile/scripts/make-icons.py`, from `web/public/icons`) on its blue.

**Not in the Android WebView**: *Import a folder…* (a folder picker is not a thing of a WebView's file chooser; import a zip instead).

## An account on a server (E17)

The app can be connected to an account on an account server (`docs/zim-server.md`, *Apps signed in*), to keep notebooks in step with other devices. As in the desktop program
(`docs/zim-desktop-shell.md`) the page's content policy is **unchanged** (it allows no network at all), so **the app makes the requests**, not the WebView, and the person signs in in
**their own browser**: the app never sees the password.

| | |
|---|---|
| The page's side | `web/src/account/native.ts`, `native-ui.ts`; `mobile/shell/shell.ts` sets `window.__zimShell.account = { request, signIn, secrets }` over the plugin below |
| The plugin | `ZimNativePlugin.java` (a Capacitor plugin of the app's own, registered in `MainActivity`: no third-party plugin) and `AccountRules.java` (the rules of what may be asked, with nothing of Android in them: tried on a plain JVM). `request`: OkHttp (the one new dependency, `com.squareup.okhttp3:okhttp:4.12.0`: `HttpURLConnection` has no PATCH, and a redirect must not be followed), for an https address, or http to this device only; an `/api/` path (the one OkHttp makes of the address: it resolves a dot segment however it is written, `%2e%2e` too, and the check reads it the same way); no name or password in it; four headers of the page's; no redirect; the system's trusted authorities, **no user-installed one** (`network_security_config.xml`, which also allows plain http to `localhost` and `127.0.0.1` only: a server being tried out); 16 MiB out and 32 MiB in. A certificate that the device does not trust is refused, and the dialog says so. `openBrowser`: ACTION_VIEW with BROWSABLE, for an https address or this device's own |
| The return | an intent filter of `MainActivity` for the scheme `org.zimnotebook.app` (the reverse of the app's id, which is what RFC 8252 asks of an address of this kind); the activity is `singleTask`, so Android gives the address to the app that is running (`appUrlOpen`). The shell takes it only if it is `org.zimnotebook.app:/callback` **with the state that was given** (any app can send this one an address like it), and waits five minutes at most; Cancel and Escape end the wait. If Android ended the app while the person was in the browser, the answer finds a new app that knows nothing of the request: the sign-in is started again |
| The token | `secretGet/Set/Remove`: AES-256-GCM with a key in the **Android Keystore** (it never leaves it), the sealed value in the app's own private preferences (and no backup of them); a value that can't be opened (a lost key) is forgotten, and the person signs in again |
| The permission | `android.permission.INTERNET`, the one, for these requests |
| The page | in Chrome the page that the app sends the person to asks *Allow this app?* (the Android app, named as such); after *Allow* the page goes to the app's address, and shows a link for the browsers that only go to an app's address when a link is pressed |

### A server whose certificate the device does not know (E17e)

A server with a self-signed certificate, or one made by an authority of the person's own (the web server's `--tls` makes one), is refused by the system's trust, and a user-installed authority is not
accepted by this app on purpose (`network_security_config.xml`). The person can instead **trust the server's own certificate by its fingerprint**, as one trusts an SSH host key. The page's side and what
the person sees are the same as in the desktop program (`docs/zim-desktop-shell.md`, *A server whose certificate the system does not know*): `window.__zimShell.account.trust = { inspect, pin, pinned, unpin }`
over the plugin, the question *Trust this server's certificate?* with the **SHA-256 fingerprint** (compared with the one that the server's own console prints), Cancel focused, and, here, what the certificate says of itself too (the
names it is for, who made it, its dates: Android's `X509Certificate` gives them), *The server's certificate has changed* with both fingerprints when it is made again, and *Look at the certificate…* in the account dialog.

| | |
|---|---|
| Looking | `trustInspect`: `PinnedTrust.look` makes a TLS handshake over a socket of its own with a trust manager that takes anything (`PinnedTrust.Look`, which is for this and nothing else: it is made in one place, and the socket is closed with nothing written to it), and reads the certificate that the server showed: **nothing is sent to a server that was not trusted yet** |
| Keeping | `trustPin` looks again and keeps the fingerprint only if the server shows that very certificate, in the app's private preferences `zim_pins` (`https://host:port` → fingerprint; no secret, no backup: `allowBackup=false`); `trustPinned`, `trustUnpin`; signing out, or connecting to another server, forgets it |
| Using | `request` looks up what is kept for the origin of the address (`AccountRules.originKey`); if there is a fingerprint the request goes through an OkHttp client whose connection has `PinnedTrust.Pin` as its trust manager: it takes **the certificate with that fingerprint as the first of what the server sent, and nothing else**, and it does so in the handshake, so **no byte of the request is sent** to a server that shows another (the failure is `certificate-changed`, which the plugin rejects with as the `code`). The host name is not what is checked then (the certificate is); there is **no fallback to what the system trusts** for that address; a trust that can't be read is no trust (the system is asked, and refuses what it does not know). One client for each fingerprint, so a connection made under one is reused only by requests that take the same |
| The other failures | `AccountRules.describe` tells a failure as about the certificate (`certificate-untrusted`) only when a certificate or its name was what the system refused somewhere in its causes (not a protocol error, not a server that is not there), with the system's own reason as a short line (*Trust anchor for certification path not found*) |

**Not done**: trusting an *authority* (a certificate made again under the same authority is asked about again); iOS (below, *An account on an iPhone*); the return by an `https` App Link (which needs a domain of our own and its `assetlinks.json`: the scheme is what works without one, and what another app could also claim; the code is worth nothing without the secret that only this app has).

## The iPhone app (D4a, D4b)

The same web files in **Capacitor's iOS project** (`mobile/ios/`, made by `cap add ios`: Swift Package Manager, iOS 17, the app's own icon and launch picture from `scripts/make-icons.py`, a shared scheme so that `xcodebuild` finds it, and `App/App.entitlements`, the keychain group below).
The shell's script is the same: on an iPhone it gives the page `saveFile` (the share sheet) and, since D4b, an **account**, through the Swift plugin below (`shell.ts` gives the page `account` only where `Capacitor.isPluginAvailable("ZimNative")`, and a page without it shows no account items).

**How it is tried** (there is no Mac here: a macOS runner of GitHub's does it, free for a public repository; job `ios` of `.github/workflows/desktop.yml`, about 6 minutes): the web build of the same run is put in the shell with a test in it
(`ZIM_E2E=1`: `mobile/test/ios-e2e.ts`, which runs in the page after the app), built for the simulator with `xcodebuild`, installed in an iPhone simulator and started by `mobile/scripts/ios-ci.sh`. A WKWebView can't be driven from outside
(Playwright does not take one, and there is no UI test target), so the test does what a person does, **from the inside, with the page's own DOM**: it types in a page and waits for it to be saved, **makes an encrypted notebook** (the vault: a Worker,
WebAssembly, the file system, scrypt at 128 MiB), locks and unlocks, and writes what it did (every step, how long, the errors the page noted, and what the WebView can do) in a file of the app's Documents folder, which CI reads from the
simulator's disk. Then the app is **terminated and started again**, and the test, which finds what is there (the line it typed), checks that the line and the encrypted notebook survived the restart, and unlocks it with the passphrase.
What happened comes out as annotations of the check (a job's log can't be read without a token) and the folder is uploaded as the artifact `ios-e2e` (with a screenshot of each run, which nobody has looked at yet).
The same test runs in a browser first (`cd mobile && npm run test:e2e-local`, Chromium or `ZIM_BROWSER=webkit`), which is how its logic was tried.

**What the first run showed** (22 October, Xcode 16.4, an iPhone 16 simulator, its WebView saying `iPhone OS 18_7`): the page is at `capacitor://localhost` and is a **secure context**; a Worker, WebAssembly, the file system (OPFS), IndexedDB and
`crypto.subtle` are all there (`SharedArrayBuffer` is not: nothing needs it); the app starts with its editor; typing is saved; **the encrypted notebook is made (the whole first run took 4.4 s)**, locks and unlocks; and after the app is
closed and started again **the line and the encrypted notebook are there** and open with the passphrase. The page noted `console.error` lines of the kind that Capacitor writes when a folder it is asked to remove is not there (the handed-over files, as on Android).

### An account on an iPhone (D4b)

The page's side is the same as on Android and in the desktop program (`window.__zimShell.account = { request, signIn, secrets, trust }`, `web/src/account/native.ts` and `native-ui.ts`), with the same rules and the same words: the page's content policy stays closed, so
**the app makes the requests**, keeps the token, and the person signs in away from the page, so that the app never sees the password. What is different is who does it.

| | |
|---|---|
| The plugin | `mobile/plugins/zim-native/`: an npm package of the app's own (`"zim-native": "file:plugins/zim-native"` in `mobile/package.json`) that `cap sync` finds and puts in `CapApp-SPM/Package.swift` and in the app's `packageClassList`. `ZimNativePlugin.swift` has the methods (`request`, `authenticate`, `cancelAuthentication`, `secretGet/Set/Remove`, `trustInspect/Pin/Pinned/Unpin`; nothing that opens an address in a browser) and four files beside it |
| The rules | `zim-native-rules/`, a Swift package with nothing of the phone in it (`Rules.swift`), run by **`swift test` on a Mac in CI** (`RulesTests.swift`): the cases of Android's `AccountRulesTest.java` and the desktop's `account.rs` (an https address, or http to this device's own; `/api/` only; no name or password; no dot segment, even written in percent; four headers; fingerprints as `openssl` says them; the words of a failure), a little stricter than Android's (a slash written `%2f` or `%5c` in the path is refused too). Foundation gives the host of `https://[::1]:8443` with its brackets on a Mac: `Rules.bareHost` takes them off for the key and for the connection (the first CI run of the rules showed it) |
| Requests | `Exchange.swift`: `URLSession`, ephemeral, no cookie, no cache, no redirect followed (a redirect is the answer), bodies and answers bounded (16 and 32 MiB), `User-Agent: ZimNotebook-iOS`. One session takes what the system trusts. For a server that has a certificate trusted for it there is a session of its own whose **challenge compares the first certificate of the chain with the fingerprint, in the handshake, before a byte of the request is sent**, and refuses anything else as `certificate-changed`: there is no fallback to what the system trusts for that address |
| Looking | `Look.swift`: a Network.framework handshake with a verify block that takes anything, reads the first certificate and closes with nothing written to it (`trustInspect`: nothing is sent to a server that was not trusted yet; `trustPin` looks again before it keeps anything) |
| Keeping | `Pins.swift`: `https://host:port` → fingerprint, in the app's preferences (it is not a secret). `Keychain.swift`: the token is a generic password of the keychain, `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` (never in a backup, never on another device); a value that can't be read is forgotten, as on Android. The keychain refuses an app that has no keychain group (error `-34018`): `App/App.entitlements` has it (`$(AppIdentifierPrefix)org.zimnotebook.app`), and a build for a simulator is signed ad hoc with it (below) |
| Signing in | `authenticate` opens the **system's sign-in sheet** (`ASWebAuthenticationSession`, an ephemeral one: no question about sharing information with the site, nothing kept of the server but the app's token) at the server's page (https, or this device's own): the person signs in there and allows the app as they would in their browser. When the server sends the browser to the app's return address, `org.zimnotebook.app.ios:/callback?code=…&state=…`, **the sheet takes the address itself**, closes, and gives it to the app, which takes the answer only if it is that address with the state that was given (`mobile/shell/callback.ts`, as on Android). The app sees nothing of the page, and **registers no scheme of its own** (`Info.plist` has none, and a test says so): no other app, and no link, can hand it an address of that kind. `cancelAuthentication` (the page's Cancel) closes the sheet. The server names the app by that address: *Zim Notebook for iPhone* in the list of what is connected, and the page asks *Allow this app?* for "the Zim Notebook app on an iPhone or iPad" (`server/src/apps.mjs`, `web/src/account/app-request.ts`) |
| The permission | `NSAllowsLocalNetworking` in `Info.plist`: a server on the device's own address may be asked over plain http, which is how one is tried out (the rules allow http to loopback only); nothing else of App Transport Security is relaxed |

**Why the sheet, and not Safari and a scheme** (as on Android). The first try was that: `UIApplication.open` at the server's page, the app registering `org.zimnotebook.app.ios` and hearing the return as `appUrlOpen`. CI could not tell whether it worked: neither `xcrun simctl openurl` nor a link of
the page handed the address to the app (in 40 and 20 seconds), which is what iOS's question *Open in the app?* for an address of a scheme that Safari or the system opens would look like; nothing here can answer it. It is also what a person would be asked, each time, with
Safari. The system's sign-in sheet exists for this: no question, a return that only this app's sheet receives, and no scheme to register. (A person's own Safari, and the account that they are signed in with there, are not used: the sheet is ephemeral, so signing in
in it is done each time, with the password manager's help.)

**How it is tried** (job `ios`, above): the same test from the inside, which now also tries what the app's own code does for an account **against a real account server on the CI's Mac** (`mobile/scripts/ios-server.mjs`: the server's own code, https with a certificate that
no system knows, plain http on the device's own address, and a few doors that only the test has, on the http side, under `/api/__e2e/`: what the server was asked, a certificate made again, and what the person's browser does to allow an app; nothing of this is in the product).
The test asks the server through the hooks, as the page does:
a request over plain http carries what an app sends and nothing of the page's (no cookie, no origin); a certificate that no system knows is refused with its code and **nothing is sent**; it is looked at in a handshake (the fingerprint is the server's own certificate's, and the server
saw no request); trusting another fingerprint is refused (`certificate-changed`) and keeps nothing, trusting the right one is kept; with it the server is asked and answers; the code that the person's browser would have got is traded for a token, which the keychain keeps and which works,
and which cannot make another token (`403`, as the server says); the server's certificate is **made again and the app refuses it before a byte is sent** (the token with it: the server saw no request) and says it changed; the new one is looked at and trusted, and the same token is good with it;
forgetting what was trusted brings the system's own refusal back; the sheet opens at the server's page, which loads in it (a Safari asks the server who is there), and closes when the sign-in is cancelled. Then the app is closed and started again: **the secret in the keychain, the
certificate that was trusted and the token are still there**, the token still works, and signing out ends it at the server. The server's own steps are in `mobile/scripts/ios-ci.sh` (it starts the server, tells the app where it is in `Documents/e2e/server.json`, runs the app twice, and
says as annotations what happened, a crash report read included).
The same test runs first in a browser (`cd mobile && npm run test:e2e-local`, Chromium or `ZIM_BROWSER=webkit`), with **stand-ins for the plugin** made by Node with the same rules and the same words (the browser is given `window.__zimShell.account`, the real server is started): that tries the test and the server's doors,
not the Swift; it was tried against 12 mutants of the stand-ins (headers of the page going on, an unknown certificate told without its code, a certificate that is not the trusted one taken, **compared after a request was sent**, a pin that compares nothing or keeps nothing, looking that sends a
request, a secret that is not kept or not forgotten, another user agent, plain http to another server), all caught by the step that should catch them.

**What the CI showed** (23 October, Xcode 16.4, an iPhone 16 simulator on iOS 26.2): the rules pass on a Mac; the plugin compiles and is found (one `Failure` that had to be an `Error`); and **the keychain needs the app to be signed with its group, which the simulator takes from the binary, not from a
signature made afterwards**: a build with `CODE_SIGNING_ALLOWED=NO` has no keychain (`-34018`, twice, even with the entitlements file in the project), the app that Xcode signs ad hoc (`CODE_SIGN_STYLE=Manual CODE_SIGN_IDENTITY=-`) puts the group in a section of the binary and its keychain works, and copies
that were re-signed by hand with the entitlements (with the group alone, with an application identifier, with a team's prefix) were all **killed at launch by the system** (`EXC_CRASH SIGKILL`, *Code Signature Invalid*, taskgated: a restricted entitlement in a signature needs a provisioning profile, which
a simulator build has not). With the app as Xcode signs it, everything above passed, before and after the restart (the secret, the certificate and the token survive it; signing out ends the token), and a secret's name that is a path is refused in its own words. **The sheet** opened at the server's page and the page loaded in it (the server saw a Safari ask for `/api/providers` and `/api/me`: 11 requests in all, 8 of them over https from the app, 3 over http from the sheet). It is not always as quick: the page was seen within twenty seconds in one run, not seen within twenty in the next (a fresh simulator each time), and seen in the last, with ninety seconds allowed: how long Safari's services take to show a first sheet varies on a runner, so the test waits for them. The job takes about twelve minutes, the whole of the iPhone's test about 25 seconds of the app's own (the encrypted notebook's scrypt included).

**Not done**: an **iPhone** (a simulator's WebView is the phone's, but its memory, its keyboard and its gestures are not; nothing of the layout, the keyboard bar or the safe areas has been looked at: the screenshots are kept and not seen); the **person's part of the sign-in**, in the sheet
(typing a password, pressing *Allow*, the sheet closing by itself on the return address: CI can open the sheet and see the server's page load in it, and cannot tap or type in it; the server's side of the grant is tried, through its own routes, by the door that stands for the person's browser);
the keychain on a **device** (a signature with a team: `$(AppIdentifierPrefix)` is then the team's, and the Keychain Sharing capability may have to be on the app's identifier); what the certificate says of itself (the names, who made it, its dates) is not given on an iPhone, as on the desktop (only its fingerprint, which is what is compared);
the share sheet (`saveFile`) was not tried; an iPad; signing, the store, and the `appId` (still a placeholder).

## The tools, installed without root

Everything is in `~/android` and nothing is installed system-wide:

```bash
# JDK 21 (Temurin) and the Android command-line tools
mkdir -p ~/android && cd ~/android
curl -sL -o jdk21.tar.gz "https://api.adoptium.net/v3/binary/latest/21/ga/linux/x64/jdk/hotspot/normal/eclipse"
mkdir jdk-21 && tar -xzf jdk21.tar.gz -C jdk-21 --strip-components=1
curl -sLO "https://dl.google.com/android/repository/commandlinetools-linux-16111833_latest.zip"   # the number changes: see repository2-3.xml
mkdir -p sdk/cmdline-tools && unzip -q commandlinetools-linux-*.zip -d sdk/cmdline-tools && mv sdk/cmdline-tools/cmdline-tools sdk/cmdline-tools/latest
# what Capacitor 8 builds with (compileSdk 36, build tools 36.0.0, Gradle 8.14.3 and AGP 8.13 come with the project), and an emulator
export JAVA_HOME=~/android/jdk-21 ANDROID_HOME=~/android/sdk
yes | $ANDROID_HOME/cmdline-tools/latest/bin/sdkmanager "platform-tools" "platforms/android-36" "build-tools/36.0.0" "emulator" "system-images/android-35/google_apis/x86_64"
```

(The newer `sdkmanager` names packages with slashes.) The emulator needs `/dev/kvm`, which this machine's user can use.

## Build, and put the app on a phone

```bash
cd web && npm run build                      # the web files of the app
cd ../mobile && npm install && npm run apk   # mobile/out/zim-notebook-debug.apk (a debug build, signed with the debug key)
# to give it out from the server that already serves the web app (the service worker lets an address that is not a file of the app through):
cd ../web && scripts/serve.sh restart --host :: --port 8443 --tls --name ADDRESS --download /zim-notebook.apk=../mobile/out/zim-notebook-debug.apk
```

Then open `https://ADDRESS:8443/zim-notebook.apk` on the phone (or copy the file over) and allow the browser to install apps from this source once.

## What verifies it

- **In a real Android WebView, on the emulator** (Android 15, `com.google.android.webview` 124, 2 cores; no phone has been tried): the app starts from
  its bundled files at `https://localhost`; `window.Capacitor` says `android`, the page is a secure context, OPFS is there, no worker is
  registered; a tap in the text brings up the system keyboard, the app shrinks to the part of the screen that is left, the formatting bar sits right
  above the keyboard and `.app.keyboard` is set; text typed is saved and is still there after the app is stopped and started; the back gesture goes
  back a page, and leaves the app at the first; *Export notebook (zip)* opens the system's share sheet with `Sample_notebook.zip`; and an
  **encrypted notebook** can be made (the vault: Worker, OPFS, WebAssembly, libsodium, scrypt at 128 MiB). That took **181 s** on the
  emulator's two emulated cores; a phone is much faster (`npm run measure:unlock` has the numbers for a browser), but it has not been measured on one.
  These were driven by hand through the WebView's DevTools socket (`adb forward tcp:9222 localabstract:webview_devtools_remote_<pid>`, then
  a small CDP client: Playwright's `connectOverCDP` does not take a WebView, `Browser.setDownloadBehavior` is not supported), with `adb` for taps,
  keys and screenshots (`mobile/scripts/emulator.sh`). They are now `npm run test:device` in `mobile/` (the basic checks: start, hooks, no worker, the exact list of
  permissions, keyboard and bar, save and restart, back twice, the share sheet; `VAULT=1` adds the encrypted notebook, minutes on an emulator; `ONLY=account` runs the account's checks alone,
  `ACCOUNT=0` leaves them out). Removing the back handling from `shell.ts` makes two of them fail.

- **The account** (E17, on the emulator, with the **real Chrome** of the emulator as the person's browser): the servers are on this machine (the account server with its own database; a second one over https
