\section*{À quoi sert ce document}
Turtlzim est une application de notes dont les notes sont au format wiki de Zim, avec chiffrement par carnet, en trois versions (web, bureau, mobile) qui partagent un seul code. Ce document garde la trace de
\textbf{ce qui a été fait, ce qui est en cours, en attente, reporté ou écarté, et ce qui reste à faire pour chaque point}. Il est repris et recompilé à chaque étape, pour qu'on puisse relire d'un coup d'œil où l'on en est.
Les chiffres de tests et les mots « vérifié » ou « non vérifié » ne disent que ce qui a réellement été exécuté ; ce qui n'a jamais été essayé est dit comme tel (section \ref{sec:nonverifie}).

\domaine{A — Fondations (format, cœur, port WebAssembly)}
\point{A1}{Format Zim : lecture et écriture}{fait}{Un lecteur/écrivain du format Zim (\code{core/zim-format}), réécrit sans copier le code de Zim. Un fichier relu puis réécrit est identique octet pour octet : test d'aléa à chaque \code{cargo test}, et test sur de vrais carnets de Zim (\code{scripts/zim-golden.sh}). Deux défauts trouvés par ces tests ont été corrigés.}{Aucune relecture extérieure. Le corpus d'essai est celui que Zim fournit : d'autres carnets réels pourraient montrer des cas rares.}
\point{A2}{Cœur Turtl en Rust remis en état}{fait}{Le cœur de Turtl (dormant, outils anciens) compile et se teste avec les outils actuels (édition 2018, async partout). Documenté dans \code{docs/core-rs-revival-notes.md}.}{Mettre à jour la libsodium d'origine du build natif (la 1.0.16 est notée dans \code{CLAUDE.md} ; à vérifier où elle sert encore).}
\point{A3}{Port WebAssembly du cœur}{fait}{Chiffrement par la vraie libsodium (libsodium.js, mêmes octets que le natif, vérifié), SQLite réel compilé en wasm, réseau asynchrone, stockage persistant (OPFS), le tout dans un Worker.}{Rien de connu côté web. Le pendant natif pour les téléphones est le point D5.}
\point{A4}{Règles du carnet}{fait}{Noms, liens, arbre, rétroliens, recherche, renommage qui garde les liens, étiquettes, journal, complétion des liens, tableaux : un seul endroit (\code{core/zim-notebook}, \code{zim-format}), appelé par l'application via wasm.}{Comparer plus largement avec le comportement de Zim sur des carnets réels (aujourd'hui : corpus de Zim seulement).}

\domaine{B — Application web}
\point{B1}{Éditeur (CodeMirror 6)}{fait}{Mise en forme vivante du texte Zim (le document \emph{est} le fichier, jamais un arbre réécrit), raccourcis, tableaux en grille, images, en-tête repliée.}{Fidélité complète à l'éditeur de Zim (risque 7 de \code{CLAUDE.md}) : syntaxes rares et réglages de Zim non reproduits.}
\point{B2}{Carnet : pages, liens, recherche}{fait}{Arbre des pages, rétroliens, recherche, renommer/supprimer, import de dossier ou de zip, export en zip.}{—}
\point{B3}{Pièces jointes et images}{fait}{Joindre, glisser-déposer, coller ; images dessinées dans la page ; une revue a trouvé et fait corriger un SVG qui s'exécutait.}{—}
\point{B4}{Journal, étiquettes, sommaire, tableaux}{fait}{Calendrier du journal, panneau d'étiquettes, sommaire de la page, complétion de \code{[[liens]]}, tableaux.}{—}
\point{B5}{Écriture sur téléphone}{fait}{Barre de mise en forme, appuis tactiles, mise en page qui suit le clavier ; testé avec des événements tactiles et un clavier simulé, en Chromium et en WebKit.}{\textbf{Jamais essayé sur un vrai téléphone} (seulement l'émulateur Android) : le comportement du clavier réel peut différer.}
\point{B6}{Application installable, hors ligne, code épinglé}{fait}{Service worker qui liste chaque fichier avec son empreinte et ne lance que la version approuvée ; mises à jour qui attendent l'accord.}{Le worker lui-même vient de l'hébergeur : un hôte hostile n'est pas arrêté, seulement rendu vérifiable (risque 6). Le paquet de bureau est la garantie la plus forte.}

\domaine{C — Chiffrement local}
\point{C1}{Carnets chiffrés (coffre)}{fait}{Cœur Turtl en wasm dans un Worker, une phrase secrète (scrypt, 128 Mio), un compte local, un « espace » par carnet ; rien de lisible ailleurs que dans le coffre (un test scanne tout ce que garde le navigateur).}{Mesurer le déverrouillage sur de vrais téléphones (181 s sur l'émulateur Android à deux cœurs émulés).}
\point{C2}{Changer la phrase, sauvegarder, restaurer}{fait}{Changement de phrase repris après un arrêt en cours de route ; sauvegarde du coffre en un seul fichier toujours chiffré ; restauration dans un autre navigateur ; coupures testées à plusieurs moments.}{Une sauvegarde ne suit pas un changement de phrase (documenté) ; clés des carnets non renouvelées par un changement de phrase.}
\point{C3}{Un seul chemin de chiffrement}{ecarte}{Règle tenue partout : libsodium seule, jamais un second code de chiffrement par plateforme.}{Écarté : tout chiffrement refait à la main ou par plateforme.}

\domaine{D — Applications (bureau, mobile)}
\point{D1}{Bureau Windows et Linux (Tauri 2)}{fait}{La même application web dans Tauri ; paquets \code{.deb}, \code{.rpm}, \code{.AppImage}, NSIS et MSI construits par GitHub Actions à chaque changement.}{macOS non fait ; signature des installeurs ; mise à jour automatique ; \textbf{jamais lancé sur une vraie machine Windows} (la CI seulement).}
\point{D2}{Carnets en vrais dossiers (bureau)}{fait}{Un carnet est un dossier Zim lu et écrit sur place, changement tout ou rien avec journal de reprise ; Zim peut ouvrir le même dossier.}{Modification simultanée avec Zim lui-même : non essayée. Sous Windows les tests du module passent maintenant sur le coureur de la CI (un déplacement qui ne changeait que la casse d'un nom échouait sur ce disque : corrigé) ; jamais essayé dans une vraie fenêtre Windows.}
\point{D3}{Android (Capacitor)}{fait}{APK de débogage, essayé dans une vraie WebView sur émulateur (quarante-quatre vérifications automatiques, celles du compte comprises) ; une seule permission, \code{INTERNET}, qui ne sert (depuis E17c) qu'aux requêtes vers un serveur de comptes que la personne a choisi : la page, elle, ne peut interroger aucun réseau. Pas de sauvegarde automatique.}{Signature de publication, boutique, \code{appId} provisoire (l'adresse de retour de la connexion en dépend : changer l'\code{appId} touche le serveur, le manifeste et la coque, et un test vérifie qu'ils s'accordent), essai sur téléphone réel.}
\point{D4}{iPhone / iPad}{attente}{Rien de commencé : le même principe (Capacitor) s'applique, WebKit est déjà testé.}{Il faut un Mac avec Xcode (ou un macOS en CI), puis un essai sur appareil.}
\point{D5}{Cœur natif relié par JNI / FFI}{reporte}{Les coques font tourner le cœur wasm dans leur WebView : ça marche et évite deux chemins de code.}{À reprendre si le coffre est trop lent sur téléphone (point C1) ; le dépôt de référence \code{turtl/mobile} montre la liaison Android.}
\point{D6}{Application Flutter / Dart}{ecarte}{Question posée le 13 octobre : non, l'éditeur serait à réécrire (plusieurs semaines, deux éditeurs à garder identiques).}{Écarté. À rouvrir seulement si l'éditeur dans une WebView s'avérait inacceptable sur appareil réel.}
\point{D7}{Interfaces natives GTK / Qt}{ecarte}{Décision du 5 octobre : une interface web partagée plutôt que trois interfaces.}{Écarté.}

\domaine{E — Comptes, serveur et sauvegardes en ligne}
\point{E1}{Étude de faisabilité}{fait}{Étude en français (\code{docs/zim-cloud-feasibility.md}) : hébergement, comptes, connecteurs, chiffrement, feuille de route en lots 0 à 8, 9 décisions ouvertes, risques.}{Les 9 décisions ouvertes (point E18).}
\point{E2}{Hébergement mutualisé OVH}{ecarte}{Lot 0 de l'étude (essai d'hébergement) abandonné le 15 octobre : on continue sur ce serveur.}{Écarté pour l'instant ; un VPS sera acheté « si le projet aboutit » (point E3).}
\point{E3}{Serveur de comptes sur cette machine}{fait}{\code{server/} : Node 24, SQLite intégré, sert l'application et \code{/api/}. Tourne sur le port 8443 (https avec certificat local).}{Mise en service pour d'autres personnes : VPS, nom de domaine, https de confiance, sauvegarde de la base, supervision, mises à jour. Rien de tout cela n'est fait.}
\point{E4}{Serveur de synchro d'origine de Turtl}{ecarte}{Remplacé de fait par \code{server/} (Node 24 + SQLite, protocole à nous) ; l'ancien (Node 8 + Postgres) n'a pas été revu.}{Écarté ; \code{CLAUDE.md} le cite encore parmi les « décisions verrouillées » : à corriger avec votre accord.}
\point{E5}{Comptes par e-mail, code à l'inscription}{fait}{Inscription (adresse + mot de passe + code à 6 chiffres envoyé une seule fois), connexion, mot de passe oublié, export des données, suppression ; mots de passe en scrypt, sessions en cookie \code{HttpOnly}, limites de tentatives, protections contre le vol de session et l'énumération.}{\textbf{Envoi réel d'e-mails jamais essayé} (sans serveur SMTP, les codes vont dans un fichier) ; SPF/DKIM ; changer le mot de passe depuis l'interface, « se déconnecter partout », vue d'administration.}
\point{E6}{Code à chaque connexion}{ecarte}{Votre décision du 15 octobre : le code seulement à l'inscription.}{Écarté.}
\point{E7}{Connexion Google et GitHub}{fait}{Flux OAuth complet côté serveur (secret jamais dans la page, PKCE, état à usage unique, liaison au navigateur, adresses confirmées par le service seulement).}{\textbf{Jamais essayé avec les vrais services} : à vous de créer les deux applications OAuth (étapes dans \code{docs/zim-server.md}), puis un essai réel.}
\point{E8}{Facebook, LinkedIn, Microsoft, GitLab (connexion)}{reporte}{Décision du 15 octobre : après Google et GitHub.}{Un pilote par service, même schéma qu'aujourd'hui ; une application OAuth à créer chez chacun.}
\point{E9}{Synchronisation en clair vers le compte (1~Mo)}{fait}{« Garder ce carnet sur le serveur » : envoi automatique, récupération, refus d'une écriture faite depuis une ancienne révision ; depuis le 16 octobre la synchronisation se fait \emph{page par page} (point E16a) : seules les pages changées voyagent, des pages différentes changées sur deux appareils se fusionnent seules. Essai à deux navigateurs avec le vrai serveur.}{Fusion à l'intérieur d'une page (aujourd'hui une même page changée des deux côtés est un conflit, avec « garder les deux ») ; quota par carnet ; les carnets de dossier du bureau et le téléphone ne se synchronisent pas encore ; la liste des empreintes tient dans le \code{localStorage} (quelques milliers de pages au plus).}
\point{E10}{Copie scellée des carnets chiffrés}{fait}{La sauvegarde du coffre (déjà chiffrée) peut être envoyée au serveur : rien de lisible n'en sort (un test examine chaque requête et le fichier stocké) ; restauration sur un navigateur sans coffre.}{Manuelle et sans fusion. La synchronisation chiffrée page par page, avec hiérarchie de clés, existe depuis le point E16d (sans clé de secours : décision du 16 octobre ; repartir à zéro : E16i).}
\point{E11}{Connecteur Nextcloud / ownCloud / WebDAV}{fait}{Le serveur appelle le service pour vous (mot de passe d'application chiffré au repos, adresses privées refusées, aucune redirection suivie) ; seuls les fichiers changés sont écrits ; essayé contre un faux serveur WebDAV.}{\textbf{Jamais essayé avec un vrai Nextcloud}. Écriture non atomique sur WebDAV.}
\point{E12}{Connecteur GitHub}{fait}{Un envoi = un commit (API Git Data), branche déplacée sans force : deux appareils ne s'écrasent pas ; essayé contre un faux GitHub.}{\textbf{Jamais essayé avec le vrai GitHub} (limites de débit, branches protégées, commits signés exigés).}
\point{E13}{Connecteur GitLab}{fait}{Un envoi = un commit avec \code{last_commit_id}, listes paginées ; essayé contre un faux GitLab.}{\textbf{Jamais essayé avec un vrai GitLab} ; la détection d'un conflit repose sur les mots de GitLab.}
\point{E14}{Connecteur Dropbox}{fait}{Autorisation dans la fenêtre de Dropbox (le serveur ne voit jamais le mot de passe), dossier d'application, jeton de rafraîchissement chiffré, révoqué quand on déconnecte ; envois par révision (un fichier modifié ailleurs n'est pas écrasé) ; essayé contre un faux Dropbox.}{À vous : créer l'application Dropbox (\code{docs/zim-server.md}) ; \textbf{jamais essayé avec le vrai Dropbox}. Pas de validation en une fois sur plusieurs fichiers (limite de Dropbox).}
\point{E15}{Connecteur Google Drive}{fait}{Autorisation dans la fenêtre de Google, portée la plus étroite (\code{drive.file}), dossier « Zim Notebooks », vrais dossiers Drive ; essayé contre un faux Drive.}{À vous : créer l'application Google ; attention, en mode « Test » Google arrête le jeton après 7 jours (à vérifier chez Google pour la publication) ; \textbf{jamais essayé avec le vrai Drive}.}
\point{E16a}{Synchro par page des carnets en clair}{fait}{Étape 1, livrée le 16 octobre : pour chaque page, on compare ce que chaque côté a changé depuis le dernier accord (comparaison à trois : base, ici, là-bas) ; envoi et récupération des seules pages changées, suppressions comprises ; pages différentes changées sur deux appareils : fusion sans question ; même page changée des deux côtés : demandée (garder les deux avec une « copie de conflit », garder la mienne, prendre l'autre), sauf si les deux versions sont identiques. Marche pour le compte et pour tous les connecteurs ; essayée à deux navigateurs contre le vrai serveur et contre des imitations de Nextcloud, GitHub, GitLab, Dropbox et Drive.}{Fusion à l'intérieur d'une page (par lignes) ; base conservée dans IndexedDB plutôt que dans \code{localStorage} pour de très gros carnets ; essai avec un réseau qui coupe en plein envoi et avec deux onglets sur un même carnet ; \textbf{jamais essayée sur un vrai service}.}
\point{E16b}{Couche de chiffrement du c\oe ur Rust}{fait}{Livrée le 16 octobre : une clé maîtresse par compte (dans le trousseau du coffre, jamais donnée en clair), une clé par carnet qui s'en déduit, des objets scellés (un par page et par pièce jointe) sous des noms qui ne disent rien, un index scellé qui porte le titre et la liste des pages ; la clé maîtresse enveloppée par la phrase du coffre (une seule phrase, décidée le 16 octobre, sans clé de secours). Huit commandes du c\oe ur, dans la liste des commandes locales (\code{seal:master:make} remplace \code{create} à l'étape E16d : elle vérifie que la phrase est celle du coffre et ne garde rien tant que le serveur n'a pas accepté la clé). Les réponses connues sont vérifiées en natif et en wasm, reproduites octet pour octet par une autre implémentation (Python), et une implémentation Node, avec la seule phrase et la clé enveloppée, rouvre ce que le navigateur a scellé.}{Utilisée par E16d. Écart avec l'étude : ChaCha20-Poly1305 (celui que le c\oe ur a sur les deux cibles) au lieu de XChaCha20, avec un nonce aléatoire de 96 bits (limite : moins de $2^{32}$ objets par clé). Pas de renouvellement de la clé maîtresse (la phrase changée l'enveloppe de nouveau).}
\point{E16c}{Pastilles et création en deux choix}{fait}{Livrée le 16 octobre : une liste unique de carnets, chaque ligne avec deux pastilles à mot (« Encrypted » ; « This device only », « Folder of this computer » ou « Synced · où · état ») ; l'état (à jour, en attente d'envoi, envoi en cours, conflit « needs you », problème, hors ligne) aussi en pastille à côté du titre, réduite à un point sur un petit écran ; la fenêtre « New notebook » demande le chiffrement et l'emplacement séparément, et envoie le carnet une première fois s'il est créé sur le serveur ou un service. Un serveur injoignable ne fait pas passer un carnet synchronisé pour un carnet local.}{Regrouper la liste par emplacement au-delà d'une dizaine de carnets ; pastilles et états dans les coques native et mobile (non essayées). (Les carnets chiffrés peuvent désormais être créés sur le serveur : E16d.) Depuis E16d aussi, le titre suit une connexion ou une déconnexion.}
\point{E16d}{Carnets chiffrés vers le serveur et les connecteurs}{fait}{Livrée le 16 octobre : un carnet chiffré se garde sur le serveur du compte ou dans un dossier d'un service connecté, \emph{scellé page par page} (un objet par page et pièce jointe sous un nom haché, un index scellé qui porte le titre et la liste des pages ; le serveur ne voit que « Encrypted notebook », un identifiant au hasard et des objets illisibles) et se synchronise entre appareils comme un carnet en clair (comparaison à trois, fusion, copie de conflit). La clé maîtresse est fabriquée par le c\oe ur, gardée par le compte \emph{enveloppée par la phrase du coffre} (comparaison-échange : deux appareils qui fabriquent la première clé en même temps n'en gardent qu'une), puis reprise dans le coffre ; un nouvel appareil crée son coffre, tape une fois la phrase qui a scellé la copie, et le carnet revient sous son nom. Un changement de phrase enveloppe la clé de nouveau (même clé) ; fait hors connexion, un message et une ligne du menu le rattrapent. Le lien d'un carnet chiffré (où il est gardé, sommes, compteur d'index vu) vit \emph{dans le coffre}, jamais dans le stockage du navigateur. Refusés : une vieille copie remise en place, un index changé, un objet manquant, remplacé par une ancienne version, abîmé ou posé sous un autre nom. Huit scénarios à deux ou trois navigateurs contre le vrai serveur et une imitation de WebDAV, qui examinent la base du serveur, les requêtes, les fichiers du service et le stockage des navigateurs. En regardant les images sur téléphone, un défaut plus ancien est apparu et a été corrigé : le menu des carnets sortait de l'écran (lignes du bas inaccessibles) ; il est maintenant ramené dans l'écran et défile (test à la taille d'un téléphone). Mutants : 16 (c\oe ur), 12 (clé côté serveur : deux avaient survécu, tests renforcés), 21 (client, dont un seul rattrapé après l'ajout d'un scénario) 31 sur les tests unitaires (remote scellé et son découpage en groupes, liens dans le coffre, appels de clé ; un avait survécu, test renforcé) et 4 sur le menu des carnets, tous attrapés à la fin.}{\textbf{Aucune copie scellée n'a été posée sur un vrai service} (Nextcloud, GitHub, GitLab, Dropbox, Drive : imitations seulement) ; pas d'essai sur téléphone ni Windows ; carnets de dossier du bureau et applications natives : reliés au serveur depuis (E17b à E17d). Phrase oubliée avec une clé qu'aucun appareil ne peut ouvrir : on repart à zéro (point E16i, fait). Pas de renouvellement de la clé maîtresse. L'index entier est renvoyé à chaque envoi (environ 170 octets par page : 170~Ko pour mille pages, sur 1~Mo de quota).}
\point{E16e}{Déplacer une page vers un autre carnet}{fait}{Livrée le 17 octobre : « Move… » parmi les actions de la page copie la page, ses pièces jointes et, si on le veut, les pages dessous (avec les leurs) vers le carnet choisi, sous le nom choisi (un nom sous le sien est permis), puis les retire du carnet d'origine : copié d'abord, retiré ensuite, donc un échec entre les deux ne perd rien (la page est alors aux deux endroits, et le message le dit). Les règles (ce qui part, ce qui gêne dans l'autre carnet, comment les liens sont réécrits pour les nouveaux noms, \emph{même quand les pages de l'autre carnet répondraient à un lien relatif à leur façon}) sont dans \code{core/zim-notebook} (\code{plan\_move}), pas dans l'application. La fenêtre dit ce que le déplacement coûte : les pages d'ici qui renvoient à ce qui part (nommées), les liens qui ne mèneront plus nulle part, et, pour une page qui sort d'un carnet chiffré vers un carnet qui ne l'est pas, qu'elle ne sera plus chiffrée (lisible par qui lit les données du navigateur, et envoyée en clair au serveur si ce carnet y est gardé) : une case à cocher est exigée. Entre deux carnets chiffrés rien ne sort du coffre. Le carnet d'arrivée n'a pas besoin d'être ouvert : il est mis à jour (et envoyé, scellé s'il l'est) quand on l'ouvre. Tests : 10 de règles en Rust, dont 4~000 plans entre carnets tirés au hasard ; 6 unitaires de la session ; 6 scénarios navigateur (carnet ouvert vers un autre ; chiffré vers ouvert avec la case ; entre deux chiffrés sans trace dans le stockage du navigateur ; vers un carnet scellé gardé sur le serveur, ouvert ensuite sur un autre navigateur ; sans autre carnet ; téléphone) ; mutants : 14 (règles), 10 (session), 10 (interface), tous attrapés. En chemin : la barre d'actions de la page, avec un septième bouton, laissait « Delete » seul sur une ligne dans une fenêtre de 860~px ; les actions se replient maintenant derrière « ⋯ » sous 58~rem (testé à six largeurs). Et WebKit gardait par référence le fichier joint rendu par IndexedDB : le retirer du carnet d'origine le rendait illisible dans l'autre, une fois sur deux ; les octets sont maintenant lus avant d'être écrits (0 échec sur 12 au lieu de 6 sur 12).}{Pas de « copier » (garder aussi la page ici), pas de glisser-déposer d'une page de l'arbre vers un carnet ; les liens des pages qui restent vers ce qui est parti ne sont pas réécrits (ils ne mènent plus nulle part, et la fenêtre le dit avant) ; \textbf{jamais essayé sur un vrai téléphone}.}
\point{E16f}{Notion de « projet » (regroupement de carnets)}{reporte}{Décision du 16 octobre : l'unité reste le carnet ; une notion de projet pourra s'ajouter si le besoin se confirme.}{À reprendre plus tard : regrouper plusieurs carnets, chacun gardant son chiffrement et son emplacement.}
\point{E16g}{Carnet mixte clair/chiffré}{ecarte}{Un carnet est soit chiffré, soit en clair, jamais les deux : les liens, rétroliens, étiquettes, recherche et arbre relient toutes les pages, et une page chiffrée à côté de pages en clair se trahirait par ces index.}{Écarté ; pourrait être repris plus tard si la pertinence est démontrée.}
\point{E16h}{Carnet mixte local/distant}{ecarte}{Un carnet est soit local, soit distant (synchronisé), jamais les deux de façon durable ; il ne l'est mélangé que pendant un changement (envoi initial, changement d'emplacement, conflit en cours).}{Écarté comme état durable ; extension possible plus tard.}
\point{E16i}{Repartir à zéro quand la phrase des copies scellées est oubliée}{fait}{Livrée le 17 octobre : dans la question « Open the key for sealed copies », un bouton « I forgot it… » mène à un avertissement qui dit ce qui disparaît (la clé du compte et ses carnets scellés dans l'espace du compte, avec leur nombre), ce qui reste (tout ce qui est sur vos appareils ; ce que tient un service connecté) et que c'est sans retour ; une case à cocher est exigée, puis le serveur supprime la clé et les carnets \code{zsl-…} en une transaction, \emph{seulement si la clé est celle que l'appareil a vue} (comparaison-échange : la clé neuve d'un autre appareil donne un 409 et rien n'est supprimé). Une première clé peut ensuite être refaite. Quand la clé d'un navigateur n'est pas celle du compte, une fenêtre propose deux sorties : oublier la clé de ce navigateur (commande \code{seal:master:forget}, qui demande la phrase du coffre, supprime l'entrée du trousseau dans les fichiers \emph{et en mémoire}), puis prendre celle du compte avec la phrase qui l'enveloppe ; ou repartir à zéro. Neuf scénarios navigateur contre le vrai serveur (dont deux ajoutés pour que les deux façons de demander la clé, ouvrir et garder, rencontrent « I forgot it… »), tests serveur (le 404, le 409, ce qui est supprimé et ce qui ne l'est pas), tests du c\oe ur en natif, en wasm32 et sur disque (l'entrée oubliée est écrasée dans les fichiers). Mutants : 3 (c\oe ur), 8 (serveur) et 9 (client), tous attrapés (deux avaient survécu côté client, tests renforcés ; le test du c\oe ur a révélé que supprimer l'entrée des fichiers ne la retirait pas du trousseau en mémoire).}{Les copies scellées des services connectés ne sont jamais supprimées par cette action (elles restent à supprimer à la main sur le service) ; un navigateur qui oublie sa clé ne rouvre plus ce qu'il avait scellé avec elle sur un service ; \textbf{jamais essayée avec un vrai service}.}
\point{E17a}{Connexion d'une application : le serveur}{fait}{Un programme ou une application de téléphone se connecte à un compte par le navigateur de la personne (RFC~8252 avec PKCE) : adresse de retour limitée au port local du programme ou au schéma propre de l'application Android, code à usage unique valable deux minutes, jeton porteur dont seule l'empreinte est gardée (six mois sans usage). Ce jeton garde des carnets mais ne peut ni en créer un autre, ni changer le mot de passe, ni supprimer le compte, ni exporter les données ; la liste des applications connectées se voit et se révoque depuis le navigateur, et un nouveau mot de passe les déconnecte toutes. Vingt tests (adresses de retour, PKCE, code à usage unique, HTTP, limites) ; 37 mutants, tous attrapés (deux avaient survécu, tests renforcés). Un défaut plus ancien corrigé en passant : la « date de session » rendue par le serveur était celle du \emph{compte}, si bien qu'un compte Google ou GitHub de plus de dix minutes ne pouvait jamais se supprimer.}{Rien côté serveur. Les applications elles-mêmes (E17b, E17c) et l'écran « Allow this app? » de l'application web sont faits ; le navigateur d'un vrai téléphone n'a jamais parlé à ce serveur (seulement le Chrome de l'émulateur, E17c).}
\point{E17b}{Connexion depuis le programme de bureau}{fait}{Livrée le 19 octobre. Le programme se connecte à un compte \emph{sans jamais voir le mot de passe} : la personne donne l'adresse du serveur (ou le programme la propose : \code{ZIM_ACCOUNT_SERVER}), le programme ouvre \emph{son} navigateur, elle s'y connecte et répond à « Allow this app? » (le bouton « Cancel » a le focus ; la page ne peut pas être mise dans un cadre), et le navigateur revient à un port que le programme a ouvert sur \code{127.0.0.1} pour \emph{une seule} réponse (bon Host, bon état, bonne page ; toute autre requête reçoit une réponse sans mettre fin à l'attente ; cinq minutes au plus). Le jeton va dans le trousseau du système (Credential Manager, Secret Service) ou, à défaut, dans un fichier à droits 600, jamais dans le stockage de la page. La politique de contenu de la fenêtre \emph{reste fermée} : c'est le programme qui fait les requêtes (https, ou http vers cette machine ; aucune redirection suivie ; les autorités de confiance du système ; un certificat refusé est dit avec sa raison). Le navigateur liste les programmes connectés et retire un programme perdu ; les services qui demandent leur propre fenêtre (Dropbox, Google Drive) s'y branchent. Un carnet chiffré se garde scellé par ce chemin comme par l'autre (scénario qui cherche son texte et son titre dans les requêtes du programme et dans la base). Tests : 18 du client, 5 scénarios navigateur (Chromium et WebKit) contre le vrai serveur avec un faux programme, 33 en Rust (dont un essai à la main contre un vrai serveur https) ; mutants : 40 du client (un équivalent, retiré) et 28 du Rust, tous attrapés. \textbf{Essai réel sur Linux} : le vrai programme (WebKitGTK, écran virtuel), le vrai serveur, un vrai Chromium pour la partie « navigateur » : connexion, carnet gardé sur le serveur avec le jeton, déconnexion (fichier du jeton supprimé, session supprimée côté serveur). Les commandes du trousseau tournent sur l'exécuteur asynchrone de Tauri (une attente de déverrouillage ne gèle pas la fenêtre) ; l'essai réel a été refait après ce changement (connexion, fichier du jeton à droits 600, déconnexion).}{Jamais essayé : Windows (Credential Manager, SChannel, \code{open}), le Secret Service de Linux (aucun démon ici : seul le repli par fichier a tourné), un certificat d'une vraie autorité, un proxy, le vrai navigateur par défaut (un \code{xdg-open} de remplacement a lancé Chromium). Un serveur à certificat auto-signé est reconnu par l'empreinte de son certificat (E17e).}
\point{E17c}{Connexion depuis l'application Android}{fait}{Livrée le 20 octobre. L'application Android se connecte à un compte comme le programme de bureau : la personne tape l'adresse du serveur, l'application ouvre \emph{son} navigateur (le vrai Chrome), elle s'y connecte et répond à « Allow this app? » (formulée pour « l'application Android »), et Android remet l'adresse \code{org.zimnotebook.app:/callback} à l'application, qui ne la prend que si elle porte l'état qu'elle a donné. Un greffon de l'application (aucun greffon tiers) fait les requêtes avec OkHttp (https, ou http vers l'appareil seulement ; chemins \code{/api/} ; quatre en-têtes ; aucune redirection ; les autorités du système seulement, pas celles qu'un utilisateur aurait ajoutées) et garde le jeton scellé par une clé du Keystore Android ; \code{INTERNET} est la seule permission et la politique de contenu de la page reste fermée. Vérifié : 4 tests JVM des règles, 3 tests unitaires de l'adresse de retour (et des endroits qui doivent s'accorder dessus : serveur, page, manifeste, \code{appId}), et sur l'émulateur (44 vérifications) le \textbf{vrai Chrome} de l'émulateur, ouvert par l'application et piloté par DevTools : connexion, une adresse envoyée par une autre application avec un autre état n'arrête pas l'attente, vrai appui sur « Allow », retour dans l'application, carnet gardé sur le serveur, toujours connecté après un redémarrage, déconnexion ; jeton scellé qui survit à un arrêt ; refus d'une adresse non https, d'un fichier, d'un certificat inconnu ; mutants : 18 (règles et retour) et 5 (greffon, essayés sur l'émulateur), tous attrapés. Une relecture avant livraison a trouvé que la règle « chemin sous \code{/api/} » lisait l'adresse brute alors qu'OkHttp résout aussi un segment « .. » écrit \texttt{\%2e\%2e} (la requête serait sortie de \code{/api/}) : corrigé, l'adresse est relue comme le client la lira ; des cas ajoutés aux tests JVM, au Rust du programme de bureau (où \code{Url::parse} le résolvait déjà) et à l'essai de l'émulateur.}{Jamais essayé : un vrai téléphone, un autre navigateur que Chrome (Firefox, Samsung Internet…), un certificat d'une vraie autorité, un serveur à certificat auto-signé sur un vrai téléphone (l'émulateur l'a fait : E17e ; une autorité ajoutée par l'utilisateur n'est toujours pas acceptée), l'application tuée par Android pendant la connexion (la réponse trouve une application neuve qui ne sait rien : on recommence), iOS.}
\point{E17d}{Carnets de dossier dans la synchronisation}{fait}{Livrée le 20 octobre. \point{E17e}{Serveur à certificat inconnu du système : épinglage de l'empreinte}{fait}{Livrée le 21 octobre. Un serveur dont le certificat est auto-signé, ou fait par une autorité de la personne (c'est ce que fait \code{--tls} du serveur web), est reconnu par l'application \emph{par l'empreinte SHA-256 de son propre certificat}, comme on fait confiance à une clé d'hôte SSH. Quand le système refuse le certificat, l'application le fait \emph{regarder} (une poignée de main TLS : rien n'est envoyé au serveur) et montre l'empreinte à la personne (sur Android, avec ce que dit le certificat : noms, émetteur, dates), qui la compare avec celle que \emph{la console du serveur} affiche au démarrage (nouvelle ligne « The server's own certificate, SHA-256 fingerprint: … » : ce n'est pas l'empreinte de l'autorité). « Annuler » a le focus ; un non ne confie rien, ne demande rien au serveur et n'ouvre pas le navigateur. Un oui garde l'empreinte, après avoir regardé le serveur \emph{une seconde fois} (ce que la personne a vu n'est pas pris pour ce que le serveur montre maintenant) ; c'est le programme ou l'application qui la garde (\code{account-pins.json}, \code{zim_pins}), jamais la page, et la requête de la page ne porte aucune empreinte. Ensuite une requête vers cette adresse ne part que sur une connexion dont le certificat est comparé à l'empreinte \emph{pendant la poignée de main, avant le moindre octet} (bureau : le TLS du système, OpenSSL ou SChannel, puis \code{hyper} sur cette même connexion ; Android : le gestionnaire de confiance d'une connexion OkHttp à part), sans repli sur la confiance du système, sans proxy, sans redirection. Un certificat refait (le serveur web en refait un par an) est refusé comme « changé » : rien n'est envoyé, l'application le dit une fois, le menu ou la fenêtre du compte mène à la question (la nouvelle empreinte et l'ancienne, « Annuler » a le focus) et un oui rend le compte \emph{avec le jeton qu'on avait}, sans nouvelle connexion. Se déconnecter oublie le jeton \emph{et} l'empreinte. Tests : 47 en Rust (dont de vrais serveurs TLS sur cette machine qui montrent l'un de deux certificats : ce que le serveur a reçu, rien quand l'empreinte ne correspond pas ; et un du module des dossiers, voir plus bas), 13 en JVM (dont un vrai serveur TLS), 30 du client (dont 12 pour cette étape), 3 d'accord entre la page, le programme et l'application, 2 du démarrage du serveur, 4 scénarios navigateur (Chromium et WebKit) contre le vrai serveur en https avec une imitation du TLS du programme, et 80 vérifications sur l'émulateur (le vrai Chrome, un certificat refait en route). Mutants : 17 (page), 4 (serveur), 19 (Rust), 12 (Java), 7 (écrans, un équivalent retiré) ; les tests trop faibles que des mutants avaient montrés ont été renforcés (une pièce jointe trop grosse et une réponse trop grosse se disaient pareil ; une empreinte donnée pour une adresse http n'était pas essayée). \textbf{Essai réel sur Linux} : le vrai programme, le vrai serveur en https (autorité à lui), un vrai Chromium comme navigateur de la personne : l'empreinte montrée par la boîte de dialogue est celle que le serveur a imprimée, rien n'a été ouvert avant le oui, le fichier des empreintes a la bonne, le certificat refait est refusé puis accepté après un oui (sans nouvelle connexion), et se déconnecter vide tout. En cours de route : un défaut ancien des boîtes de dialogue (le message d'une tentative restait à l'écran pendant la suivante) est corrigé.}{Windows : la CI y lance maintenant \code{cargo test}, et les tests TLS y passent avec le vrai SChannel (serveurs TLS de test, poignée de main sans vérification du système, empreinte comparée avant tout octet) ; elle a aussi trouvé un défaut \emph{ancien} du module des dossiers, corrigé : un déplacement qui ne change que la casse d'un nom (« Case/a.png » vers « case/A.png ») échouait, et était défait, sur un disque qui ignore la casse. Jamais essayé : une vraie fenêtre Windows, un vrai téléphone, un certificat d'une vraie autorité, un proxy. Pas fait : faire confiance à une \emph{autorité} (un certificat refait sous la même autorité est redemandé), montrer sur le bureau plus que l'empreinte (noms, dates : Android le montre), les dates et les noms du certificat ne sont pas vérifiés (l'empreinte dit quel certificat). Comme avec une clé SSH, la première confiance est une confiance sur parole : si la personne ne compare pas l'empreinte, quelqu'un qui est entre elle et le serveur à ce moment-là gagne (la fenêtre le dit).}

\section{Principes d'organisation des carnets}\label{sec:principes}
Décidés le 16 octobre 2026, avec le vocabulaire : \textbf{carnet} (l'unité), \textbf{page} (une note ; une page peut avoir des sous-pages, ce qui donne les sections), \textbf{pièce jointe}. Ces règles sont des \emph{choix}, pas des limites techniques :
elles pourront être assouplies plus tard si l'usage le justifie.

{\footnotesize\setlength{\tabcolsep}{4pt}\renewcommand{\arraystretch}{1.2}
\begin{longtable}{@{}p{2.6cm} p{7.1cm} p{7.1cm}@{}}
\toprule \textbf{Axe} & \textbf{Règle retenue} & \textbf{Extension possible plus tard}\\ \midrule\endhead
Chiffrement & Un carnet est \textbf{soit chiffré, soit en clair} : il ne contient jamais à la fois des pages chiffrées et des pages en clair. L'unité de chiffrement est le carnet (une clé par carnet). &
Carnet mixte (quelques pages chiffrées dans un carnet en clair), si on trouve comment ne rien révéler par les liens, rétroliens, étiquettes, recherche et arbre. Aujourd'hui : un second carnet chiffré et la fonction « déplacer la page » (E16e, faite). \\ \midrule
Emplacement & Un carnet est \textbf{soit local} (seulement sur cet appareil), \textbf{soit distant} (synchronisé : compte du serveur ou service connecté), une seule destination à la fois. Il ne mélange pas de pages locales et de pages distantes, \textbf{sauf temporairement} pendant un changement (envoi initial, changement d'emplacement, conflit en cours de règlement). &
Carnets dont certaines pages ne quittent jamais l'appareil ; plusieurs destinations à la fois pour un carnet. \\ \midrule
Stockage et synchronisation & Un carnet distant est stocké \textbf{page par page} (un objet par page et par pièce jointe) avec un index ; seules les pages changées voyagent ; deux appareils qui changent des pages différentes se fusionnent seuls. Un carnet chiffré suit le même schéma, avec des objets scellés. &
Découpage plus fin à l'intérieur d'une page (fusion de lignes) ; compactage de l'index pour de très gros carnets. \\ \midrule
Phrase secrète & Les carnets chiffrés (locaux ou distants) réutilisent \textbf{la phrase du coffre local} : une seule phrase, jamais redemandée pour la même session. Une phrase perdue = carnets perdus (aucune clé de secours aujourd'hui ; un « repartir à zéro » pour la clé du compte existe, E16i). &
Clé de secours imprimée une fois ; phrase propre à chaque carnet. \\ \midrule
Interface & Une \textbf{liste unique} de carnets ; deux pastilles avec un mot : « Chiffré » et « Synchronisé (où) » ou « Cet appareil seulement » ; une icône d'état (à jour, envoi en cours, conflit, erreur). &
Regroupement par destination au-delà d'une dizaine de carnets ; regroupement de carnets en « projets » (E16f). \\
\end{longtable}}

\item Aucun envoi réel d'e-mail, aucune charge, aucun essai avec plusieurs processus serveur.
\item Aucun vrai téléphone, aucune machine Windows réelle, aucun Mac.
\item L'application Android connectée à un compte n'a tourné que sur l'émulateur (Chrome 124, image userdebug), vers des serveurs de cette machine joints par \code{adb reverse} ; jamais sur un vrai téléphone, avec un autre navigateur, ni avec un certificat d'une vraie autorité.
\item Le programme de bureau connecté à un compte n'a tourné que sur Linux, sans trousseau système (le repli par fichier a servi), vers un serveur en http sur la même machine, avec un autre navigateur lancé à la place du navigateur par défaut ; un certificat d'une vraie autorité, un proxy, Windows n'ont jamais été essayés.

\section{Risques ouverts}
\begin{itemize}
\item \textbf{Confiance dans le code servi par le web} (risque 6) : atténuée par le service worker, non résolue ; le paquet de bureau est la meilleure garantie.
\item \textbf{Notes en clair sur le serveur} : un carnet \emph{en clair} « gardé sur le serveur » ou sur un connecteur est lisible par l'exploitant du service (les fenêtres le disent) ; un carnet \emph{chiffré} est scellé (E16d), mais l'exploitant garde toutes les versions envoyées et peut essayer des phrases hors ligne : une phrase faible est la seule faille.
\item \textbf{Phrase secrète oubliée} : aucune récupération possible (coffre et copies scellées) ; dit avant chaque activation. Un compte dont la clé ne peut plus s'ouvrir se remet à zéro depuis la question de la clé (E16i), ce qui supprime ses copies scellées du serveur.
\item \textbf{Jeton d'une application native volé} : un jeton porteur vaut cent quatre-vingts jours ; il ne garde que des carnets (il ne change pas le mot de passe, n'exporte rien, ne supprime pas le compte et ne crée pas d'autre jeton) et se révoque depuis le navigateur (liste « Connected apps »). Sur Android une clé du Keystore le scelle ; sur le bureau il est dans le trousseau du système, ou, à défaut, dans un fichier à droits 600 que lit tout programme de la même personne.
\item \textbf{Première confiance à une empreinte} : comme avec une clé d'hôte SSH, la première fois se fait sur parole. La personne compare l'empreinte montrée avec celle que la console du serveur imprime ; si elle ne le fait pas, quelqu'un qui se trouve entre elle et le serveur à ce moment-là peut se faire reconnaître. Ensuite seul ce certificat est accepté pour cette adresse, et tout autre est refusé et redemandé (un certificat qui change est un événement, pas un détail). Aucune autorité n'est jamais ajoutée à la confiance de l'appareil.
\item \textbf{Dépendance à de petites imitations pour tester les services} : un vrai service peut répondre autrement ; d'où la liste de ce qui reste à essayer.
\item \textbf{Fidélité à Zim} (risque 7) : l'essentiel est couvert, pas tout.
\end{itemize}
